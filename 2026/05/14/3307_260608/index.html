[SEED 5월호] CVE-2025-22225: VMware VMX Arbitrary Write 취약점

author: ssseo Posted on 2026-05-14 In S.E.E.D. series

1. Summary

VM에 관해서 하이퍼바이저(Hypervisor)에 대해서 들어본 적 있으신 가요? 하이퍼바이저는 하나의 물리적 컴퓨터, 즉 호스트에서 여러 개의 가상 머신을 동시에 실행하고 관리할 수 있게 해주는 소프트웨어 계층입니다.

정상적인 가상화 환경에서 하이퍼바이저(Hypervisor)는 물리적 하드웨어를 제어하고, 가상 머신(VM)은 그 위에서 철저히 격리된 샌드박스 형태로 실행됩니다. 하지만 가상 머신 내부의 권한을 탈취한 공격자가 하이퍼바이저의 취약점을 통해 호스트 시스템 전체를 장악하는 것을 ‘VM Escape(가상 머신 탈출)’라고 부르며, 이는 가상화 환경에서 가장 치명적인 위협입니다.

2025년 3월 공개된 CVE-2025-22225는 VMware ESXi 및 관련 인프라 환경에서 발생하는 치명적인 임의 메모리 쓰기(Arbitrary Write) 취약점입니다. 이 취약점은 단일 가상 머신(VM)의 권한 경계를 넘어, 호스트 시스템(Hypervisor) 전체의 제어권을 탈취할 수 있는 샌드박스 탈출을 유발합니다.

특히 이 취약점은 단독으로 쓰이기보다 랜섬웨어 공격 조직이 3개의 심각한 취약점(CVE-2025-22224, 22226, 22225)을 연쇄적으로 엮어 만든 ‘ESXicape 익스플로잇 체인’의 핵심 단계로 적극 악용되었습니다(*CVSS 8.2). 그렇기에 신속한 보안 패치 및 아키텍처 수준의 완화 조치가 요구됩니다. 이번 분석에서는 해당 취약점의 근본 원인, PoC 코드의 구조적 분석, 실제 랜섬웨어의 공격 시나리오, 그리고 심화 방어 전략을 종합적으로 다뤄보고자 합니다.

  • CVSS(Common Vulnerability Scoring System, 공통 취약점 평가 시스템)
    : 소프트웨어나 시스템의 보안 취약점이 얼마나 심각하고 위험한지를 0점에서 10점 사이의 숫자로 나타내는 국제 표준 지표


2. 취약점 개요 및 타겟 환경

2.1. 취약점 기본 정보

  • CVE ID: CVE-2025-22225
  • 취약점 유형: 임의 메모리 쓰기 (Arbitrary Write)
  • 위험도 (CVSS): 8.2점 (고위험)
  • CISA KEV 등재: 2025년 3월 4일 (26년 5월, 현재 실제 사이버 공격에 활발히 악용되고 있음이 공식 확인됨)

2.2. 영향을 받는 시스템(Affected Versions)

본 취약점은 대규모 기업 인프라 및 데이터 센터에서 광범위하게 사용되는 VMware 핵심 인프라에 영향을 미칩니다. 분석 및 모의 침투를 위해 환경을 구축할 때는 아래의 정확한 빌드 넘버를 참조하여야 합니다.

  • VMware ESXi 8.0: ESXi80U3d-24585383 및 ESXi80U2d-24585300 미만 버전
  • VMware ESXi 7.0: ESXi70U3s-24585291 미만 버전
  • VMware Cloud Foundation: 5.x 및 4.5.x 라인업
  • VMware Telco Cloud Platform: 5.x, 4.x, 3.x, 2.x

3. 취약점 발생 원리

3.1. VMX 프로세스와 격리의 붕괴

정상적인 가상화 환경에서 게스트 VM은 호스트 커널 및 메모리와 엄격하게 분리되어 있습니다. 게스트 운영체제가 CPU, 메모리 또는 네트워크 디바이스와 통신해야 할 때, 하이퍼바이저 위에서 구동되는 VMX (Virtual Machine Executable) 프로세스가 이를 중재하여 에뮬레이션합니다.

CVE-2025-22225는 이 VMX 프로세스 내의 특정 가상 디바이스 인터페이스에서 메모리 기록에 대한 유효성 검사가 누락되어 발생합니다.

3.2. Out-of-bounds Write (CWE-787) 및 Write-What-Where 조건의 성립 (CWE-123)

해당 취약점의 근본적인 원인(Root Cause)은 NVD 공식 분류에 따라 소프트웨어가 의도된 메모리 버퍼의 끝을 지나거나 시작하기 전의 위치에 데이터를 기록하게 되는 CWE-787 (Out-of-bounds Write)에 있습니다. 이러한 취약점은 통상적으로 메모리 손상(Memory Corruption)을 유발하며, 결과적으로 프로세스의 충돌(Crash)을 일으키거나 의도치 않은 임의 코드 실행(Code Execution)으로 이어질 수 있습니다.

VMware 환경에 이를 대입해 보면, 공격자가 제어 가능한 가상 환경 내에서 특수하게 조작된 I/O 포트 명령이나 VMCI(Virtual Machine Communication Interface) 패킷을 전송할 때 문제가 발현됩니다. VMX 프로세스는 이를 파싱하여 호스트 커널에 기록하게 되는데, 전달받은 패킷의 길이나 목적지 오프셋이 버퍼 내에 속해 있는지 확인하는 경계 검사(Boundary Check) 로직이 누락되어 있습니다.

이렇게 버퍼 경계를 벗어난 위치에 데이터를 쓸 수 있게 방치됨으로써, 익스플로잇 기법(Primitive)으로서의 CWE-123 (Write-what-where) 조건이 완벽히 성립됩니다. 결과적으로 공격자는 아래의 두 가지 핵심 요소를 완전히 통제할 수 있는 권한을 얻게 됩니다.

  • What: 공격자가 의도한 악의적인 페이로드(예: 쉘코드, 권한 상승 플래그)
  • Where: 호스트 커널 공간 내의 임의의 메모리 주소(예: 자격 증명 구조체, 함수 포인터 테이블)

그림 4. [PoC 구조 상세 분석 1]

공격 패킷(구조체) 정의 - 이 구조체는 공격자가 VMX 프로세스에 전달할 ‘악의적인 데이터 패킷’의 형태를 정의합니다. Arbitrary Write 공격의 두 가지 핵심 요소인 ‘어디에 쓸 것인가(Where)’와 ‘무엇을 쓸 것인가(What)’를 공격자가 100% 통제할 수 있도록 변수를 선언한 것입니다.

그림 5. [PoC 구조 상세 분석 2]

타겟 주소 획득 및 ASLR 우회 (kernel_address) - 여기서 0xffffffffdeadbeef는 개념 설명을 위한 임의의 더미 값이지만, 실제 공격에서는 가장 고난도의 단계입니다. 호스트 커널은 메모리 주소가 무작위로 바뀌는 ASLR(주소 공간 배열 무작위화) 기법으로 보호되고 있기 때문에, 공격자는 사전에 정보 유출 취약점을 연계하여 호스트의 실제 메모리 베이스 주소를 구한 뒤, 타겟 구조체의 정확한 오프셋을 계산하여 이 변수에 삽입해야 합니다.

페이로드 주입 - 타겟 주소에 덮어쓸 값을 결정합니다. 코드 예시처럼 프로세스의 권한(Credentials)을 관리하는 영역을 타겟팅하여 Null(0x0)로 덮어씌워 권한 검증을 무력화(Root 권한 획득)할 수도 있고, 가상 함수 테이블(vftable)이나 반환 주소(Return Address)를 덮어씌워 공격자가 미리 준비해 둔 쉘코드(Shellcode)로 실행 흐름(Control Flow)을 돌려버릴 수도 있습니다.

그림 6. [PoC 구조 상세 분석 3]

취약점 트리거 및 샌드박스 붕괴 - 게스트 OS가 호스트와의 합법적인 통신 인터페이스(ioctl, VMCI 등)를 통해 앞서 조작한 구조체를 전송하는 순간입니다. 하이퍼바이저(VMX) 내부에서는 게스트로부터 전달받은 kernel_address가 접근이 허용된 안전한 버퍼 내에 속해 있는지 확인하는 경계 검사(Boundary Check) 로직이 누락되어 있습니다. 결국 VMX는 의심 없이 호스트 커널 영역에 페이로드를 기록해버리며, 이 순간 가상 머신의 샌드박스가 완전히 붕괴됩니다.



5. 실제 침해 사고 체인 (The ESXicape Kill-Chain)

CVE-2025-22224, CVE-2025-22225, CVE-2025-22226 단독 취약점은 하나의 VM escape chaining으로 활용되고 있습니다. Sygnia, Lorikeetsecurity, Huntress 등의 위협 인텔리전스 분석 보고서에 따르면, APT 및 랜섬웨어 그룹은 이 취약점을 단일 공격으로 끝내지 않고 정교한 체인으로 엮어 사용하고 있음을 알 수 있습니다. 실제 침해 사고 관점에서의 익스플로잇 흐름은 다음과 같습니다. (※ Lorikeetsecurity와 Huntress 보고서 간에 악성 서비스가 등록되는 inetd 포트 번호 등 세부 사항에서 두 가지 관점 차이가 존재하긴 합니다.)

  • 초기 침투 경로: 외부 인터넷에 노출된 SonicWall VPN 취약점 등을 통해 최초 거점을 확보한 뒤, 내부망의 타겟 Windows 게스트 VM 관리자 권한을 탈취합니다.

  • Phase 1. VMCI 드라이버 비활성화: 익스플로잇을 수행할 악성 커스텀 드라이버가 VMCI(Virtual Machine Communication Interface) 통신 채널을 독점해야 하므로, 기존 정상 드라이버를 강제로 내립니다.

    • 사용 도구: 정상 유틸리티 devcon.exe 악용
    • 실행 명령어: devcon.exe disable “PCI\VEN_15AD&DEV_0740”
      →호스트와의 기존 통신이 끊어지며 악성 통신을 위한 준비 완료

  • Phase 2. 악성 드라이버 로드: Windows 커널 메모리에 공격자의 익스플로잇 페이로드(MyDriver.sys)를 주입합니다.
    • 사용 기법: BYOVD (Bring Your Own Vulnerable Driver)

  • Phase 3. CVE-2025-22226 (VMX 메모리 유출 - HGFS) ASLR을 우회하기 위해 VMX 프로세스의 베이스 주소를 유출하는 단계입니다.
    • 베이스 주소 계산 흐름:
    • 메모리 Leak 유도 명령어: tools.capability.hgfs_server toolbox-dnd 1
    • Leak 트리거 페이로드 형태: 4F 4B 20 00 00 00 00 FF 00 00 00 A5 C5 00 00 A4 C5 00 00 00 00 00 80 29 00 00 00 + [50573 zeros]
    • 검증 및 연산: 유출된 포인터(leakedPtr)를 검증한 뒤 베이스 주소를 계산합니다. vmxBase = leakedPtr - 0x01590300;

  • Phase 4. CVE-2025-22224 (VMX 쉘코드 주입 - VMCI) 계산된 VMX 베이스 주소를 바탕으로, 메모리 손상을 일으켜 실행 흐름(Control Flow)을 탈취합니다.

  • Phase 5. CVE-2025-22225 (커널 탈출 및 백도어 설치): 마지막으로 임의 쓰기(Arbitrary Write) 취약점을 통해 호스트 커널 계층까지 장악하며 VM Escape를 완성합니다.
    • 지속성 확보 (inetd 등록):
      탐지를 회피하고 호스트에 지속적으로 접근하기 위해 /etc/inetd.conf 파일에 백도어 서비스를 등록합니다. (※ 공격 그룹에 따라 바인딩 포트에 차이가 존재합니다.) (inetd.conf 추가 내용 예시: 8000 stream tcp nowait root /bin/sh -i)

  • Impact: VM 샌드박스를 뚫고 호스트 장악에 성공한 공격자는 vCenter 통제권을 확보하여, 전체 VM에 랜섬웨어를 동시다발적으로 배포하고 데이터스토어 백업을 영구 삭제합니다.



6. 대응 및 완화 전략

CISA SSVC 평가 기준 “Automatable: No”라는 지표에서 알 수 있듯, 공격은 네트워크 웜처럼 무작위로 확산되지 않으며 게스트 내부 관리자 권한이 선행되어야 합니다. 따라서 구조적인 하드닝(시스템, 서버, 네트워크, 애플리케이션의 보안 취약점을 줄여 공격 표면을 최소화하는 모든 일련의 과정)을 통해 피해를 통제할 수 있습니다.

6.1. 우선순위 완화 조치

  • Patch Management: Broadcom 공식 권고안(0/25390)에 따라 가장 취약한 버전을 우선 식별하여 48시간 내에 패치를 진행해야 합니다.
  • Network Segmentation: 인프라 설계 시 DMZ 영역과 내부 핵심 데이터베이스 구역의 ESXi 호스트 및 데이터스토어를 물리적/논리적으로 분리하여 최대 피해 범위를 제한해야 합니다.

6.2. 시스템 하드닝 (Hardening)

  • SSH 서비스 비활성화: ESXi 호스트의 SSH는 유지보수 목적 이외에는 항시 비활성화 상태를 유지합니다.
  • Lockdown Mode 적용: vCenter를 통하지 않은 호스트 직접 접근을 차단하기 위해 ESXi Lockdown 모드를 활성화합니다.
  • 모니터링 강화: VMX 프로세스 기반의 비정상 메모리 읽기/쓰기 시도를 탐지하기 위해 커널 레벨의 이벤트 로그 분석 시스템을 구축합니다.

6.3. 코드 레벨 패치 방향 (Code-Level Patch)

운영 환경 보안 뿐만 아니라 취약점 자체를 해결하기 위한 코드 레벨의 패치 구조가 필수적입니다. 이전 버전의 VMX 프로세스는 게스트가 조작한 메모리 주소(Raw Pointer)를 검증 없이 호스트 커널에서 직접 역참조하는 치명적인 논리적 결함을 가지고 있었습니다.

웹 검색을 통해 최신 공개 취약점 데이터베이스와 GitHub 등을 확인해 보았으나, CVE-2025-22225 및 ‘ESXicape’ 체인과 관련된 실제 제조사(VMware)의 공식 패치 소스코드는 아직 외부에 공개되지 않았거나, 학술 연구 및 모의 훈련을 위해 구성된 시나리오일 가능성이 높은 것 같습니다.

하지만 실제 VMware 하이퍼바이저(VMX) 환경에서 이러한 형태의 Arbitrary Write 취약점(CWE-787)이 발생했을 때, 이를 방어하기 위해 적용되는 산업 표준 C 언어 보안 패치 패턴이 존재하기에 이를 바탕으로 패치코드를 구상해보았습니다.

[패치 전: 취약한 소스 코드]

그림 7. [패치 전 소스코드]

게스트가 전달한 구조체 내의 kernel_address를 아무런 경계 검사(Boundary Check) 없이 신뢰하여 호스트 커널 메모리에 데이터를 덮어씁니다.

[패치 후: 안전한 소스 코드]

그림 8. [패치 후 소스코드]

게스트로부터 전달된 Raw Pointer를 호스트 메모리에 직접 매핑하는 기존 방식을 전면 폐기해야 합니다. 요청된 주소가 샌드박스 내부 영역인지 1차 검증을 수행하고, 안전한 Wrapper 함수를 통해서만 제한적인 쓰기를 허용하도록 로직을 변경합니다.

패치 로직의 핵심

  • 입력값 검증: VMX_IsSafeGuestMemoryRegion()과 같은 함수를 통해 게스트가 요청한 메모리 주소가 권한이 허가된 샌드박스 내부인지 사전에 확인합니다.
  • 직접 메모리 참조 제거: 원시 포인터를 호스트 메모리에 직접 역참조하는 로직을 제거하고, 프레임워크에서 제공하는 메모리 매핑 함수(VMX_MapGuestToHostAddress)를 사용하여 안전하게 데이터를 기록합니다.


7. 결론

CVE-2025-22225 취약점은 현대 엔터프라이즈 환경에서 “가상 머신 내부의 침해가 어떻게 호스트 계층 전체의 무력화로 이어질 수 있는지”를 보여주는 완벽한 사례입니다. 가상화 샌드박스는 커널 보호 기법이 무너지는 순간 무용지물이 됩니다. 보안 조직은 단순한 패치를 넘어 인프라 전반의 망 분리, 권한 통제, 그리고 메모리 포렌식 기반의 위협 헌팅 역량을 지속적으로 강화해야 합니다.
