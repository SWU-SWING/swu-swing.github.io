[SEED 6월호] CVE-2025-24813: Apache Tomcat의 Path Equivalence 취약점

author: kminix Posted on 2026-06-19 In S.E.E.D. series

1. 개요

CVE-2025-24813은 쓰기 권한이 할당된 Default Servlet의 partial PUT 임시 파일 처리 과정에서 발생하는 Path Equivalence 취약점이다. Path Equivalence 취약점은 경로 동등성 문제로, 서로 다른 문자열 경로가 내부적으로는 동일한 파일이나 디렉터리를 가리키도록 해석될 수 있다는 점을 악용한다. 환경 조건에 따라 민감 파일의 정보 노출 및 내용 변조로 이어질 수 있으며, 추가로 파일 기반 세션 저장과 역직렬화 공격에 악용 가능한 라이브러리가 결합되면 원격 코드 실행으로 확장될 수 있다. 이 글에서 해당 취약점의 발생 조건, 동작 원리, 실습 환경에서의 재현 방식, 대응 방안과 더불어 공급망 보안 관점에서의 해석을 다룬다.



2. CVE-2025-24813의 기본 정보 및 배경 지식

CVE-2025-24813
대상 Apache Tomcat
핵심 조건 Default Servlet 쓰기 기능 활성화, partial PUT, FileStore 기반 세션 저장 사용, 역직렬화 가능 라이브러리 등
영향 원격 코드 실행, 정보 노출, 파일 변조

패치 버전 9.0.99, 10.1.35, 11.0.3 이상

위 표에서도 볼 수 있듯, 해당 취약점에 대해 분석하기 위해서는 발생 조건의 핵심에 해당하는 Default Servlet, partial PUT, FileStore 기반 세션 저장에 대한 이해가 선행되어야 한다.

2. 1. Default Servlet

Tomcat의 Default Servlet은 정적 파일을 제공하는 기본 서블릿이다. 보통 HTML, 이미지, JavaScript, CSS 같은 정적 리소스를 처리한다. 기본 설정에서는 ‘readonly=true’로 쓰기 기능이 비활성화되어 있어 PUT과 DELETE 요청을 거부한다. 반대로 ‘readonly=false’로 값을 설정한다면 PUT 요청을 통한 파일 생성 및 수정과 DELETE 요청이 허용된다.

2. 2. partial PUT

partial PUT은 명칭 그대로 HTTP ‘Content-Range’ 헤더를 사용해 파일의 전체가 아닌 일부 범위만을 업로드하는 방식이다. 이 기능은 기본적으로 활성화되어 있다.

아래는 partial PUT이 무엇인지, HTTP ‘Content-Range’가 어떻게 쓰이는지를 보여주는 예시다. 파일의 전체 1000바이트 중, 200번부터 299번 위치만 업로드하겠다는 의미다.

중요한 점은, partial PUT 자체만으로 문제가 발생하는 것이 아니라, 위에서 언급한 ‘readonly=false’ 조건까지 결합되어야 해당 취약점을 트리거할 수 있다는 것이다. 취약한 Tomcat 버전의 partial PUT 구현은 사용자로부터 전달된 파일명과 경로를 기반으로 임시 파일을 생성하고, 이 과정에서 경로 구분자 ‘/’를 ‘.’으로 치환했다. 이로 인해 서로 다른 URL 경로가 내부적으로 동일한 partial PUT 임시 파일명으로 매핑될 수 있는 Path Equivalence 문제가 발생할 수 있다.

위의 두 경로는 URL 관점에서 서로 다른 리소스를 가리킨다. 첫 번째는 uploads 디렉터리 아래의 private.report.pdf 파일을 의미하고, 두 번째는 uploads/private 디렉터리 아래의 report.pdf 파일을 의미한다. 그러나 partial PUT 임시 파일명을 만들 때 경로 구분자 ‘/’가 ‘.’으로 치환되면, 두 경로 모두 ‘.uploads.private.report.pdf’로 변환될 수 있어 동일한 임시 파일을 참조할 수 있게 된다. 다시 말해 실제 웹 애플리케이션의 최종 파일 경로가 완전히 같아진다는 의미가 아니라 서로 다른 리소스의 partial PUT 처리 과정에서 임시 파일이 충돌해 내용이 변조될 수 있다.

2. 3. FileStore 기반 세션 저장

Tomcat은 설정에 따라 세션 정보를 파일로 저장할 수 있다. 이때, 세션은 ‘.session’ 파일 형태로 저장되며 이후 동일한 세션 ID가 요청되면 Tomcat이 해당 파일을 읽어 세션을 복원한다. 원격 코드 실행 시도가 이 FileStore 기반 세션 저장과 연결된다. 공격자가 partial PUT을 이용해서 조작된 세션 파일을 Tomcat의 기본 세션 저장 위치에 위치시킬 수 있고, 이후 JSESSIONID 값을 조작하여 Tomcat이 해당 세션 파일을 로드하도록 유도할 수 있다. 세션 복원 과정에서는 직렬화된 세션 데이터를 Java 객체로 되돌리는 역직렬화를 수행한다. 이 과정에서 공격자가 조작한 세션 파일을 Tomcat이 신뢰하고 읽게 만들 수 있고, 애플리케이션 classpath에 역직렬화 공격에 악용 가능한 라이브러리나 *gadget이 존재할 경우 원격 코드 실행 공격이 가능해질 수 있다.

(*gadget: 역직렬화 과정에서 호출되어 잠재적으로 위험한 동작을 수행하는 메서드)


3. 취약점 동작 조건

CVE-2025-24813은 미칠 수 있는 영향에 따라 충족 조건이 상이하다는 것이 핵심이다. 영향은 크게 정보 노출 및 파일 변조와 원격 코드 실행 두 가지로 나눌 수 있다. 이 분류에 따라 취약점 동작 원리에도 차이가 있다. 아래의 항목에서 취약점 작용의 조건을 정리해 보았다.

3. 1. 정보 노출 & 파일 변조

  • Default Servlet 쓰기 허용: ‘readonly=false’ 등으로 쓰기 기능 활성화
  • partial PUT 기능 활성화
  • 업로드 경로 구조: 민감한 업로드 URL이 공개 업로드 URL의 하위 디렉터리인 경우
  • 파일명 정보: 공격자가 업로드되는 민감 파일명을 알고 있는 경우
  • 민감 파일도 partial PUT 사용: 해당 파일 역시 partial PUT 방식으로 업로드되는 경우

정보 노출과 파일 변조 공격의 경우, 위에서 언급했던 Path Equivalence 문제와 더불어 민감한 파일의 정보, 민감 파일의 partial PUT 사용 조건이 모두 충족되어야 한다.

3. 2. 원격 코드 실행

  • Default Servlet 쓰기 허용: ‘readonly=false’ 등으로 쓰기 기능 활성화
  • partial PUT 기능 활성화
  • FileStore 기반 세션 저장: Tomcat의 파일 기반 세션 저장을 기본 위치로 사용하는 경우
  • 역직렬화 gadget 존재: 애플리케이션 classpath에 역직렬화 공격에 악용 가능한 라이브러리가 있는 경우

원격 코드 실행 공격의 경우, partial PUT으로 얻은 파일 쓰기 권한과 FileStore 기반 세션 복원 및 Java 역직렬화와 연결될 때 발생한다.

4. 2. 실습 과정

앞서 언급한 두 단계는 아래와 같은 흐름으로 실현할 수 있다.

(1) 1 단계: ‘Content-Range’ 헤더가 포함된 PUT 요청으로 직렬화된 세션 파일을 서버에 위치시킨다. 아래는 Tomcat 디렉터리에 .poc.session 파일을 생성하는 요청이다.

(2) 2 단계: ‘Cookie: JSESSIONID=.[filename]’ 요청으로 Tomcat이 해당 세션 파일을 로드하도록 유도한다. JSESSIONID=.poc를 사용하여 FileStore가 .poc.session을 로드하고, 세션 역직렬화 과정에서 검증용 SessionProbe.readObject() 가 호출되는지 확인해 주었다.

큰 흐름을 잡아두었으니, 다음으로는 충족 조건들을 점검해주어야 한다.

조건 1. Default Servlet의 readonly = false 설정

그림 2. [Default Servlet의 readonly 값이 false로 설정된 모습]

‘readonly=false’로 설정하여 Default Servlet에서 PUT 요청을 통한 파일 쓰기가 가능하도록 구성하였다.

조건 2. Partial PUT 요청 처리

그림 3. [Content-Range 헤더를 포함한 PUT 요청 처리 및 결과]

Content-Range 헤더를 포함한 PUT 요청을 전송하였다. Tomcat의 DefaultServlet.doPut()은 먼저 readonly 값을 확인하고, parseContentRange()로 Content-Range 헤더를 해석한다. partial PUT으로 판단되는 경우, executePartialPut()을 호출해 임시 파일을 만든 뒤 resources.write()로 최종 리소스를 기록한다. HTTP/1.1 201 응답을 통해 Tomcat이 이 요청을 정상적으로 처리하여 /poc.session 리소스를 생성했음을 확인할 수 있다.

조건 3. FileStore 기반 세션 저장 설정

그림 4. [PersistentManager와 FileStore 설정]

context.xml에 PersistentManager와 FileStore를 설정하여 Tomcat이 세션 파일을 기본 디렉터리에 저장하고, 다시 로드할 수 있도록 구성하였다.

조건 4. .session 파일 업로드 흐름 확인

그림 5. [partial PUT 처리 후 생성된 세션 관련 파일]

partial PUT 요청 이후 Tomcat의 파일 시스템을 확인해보면, 기본 디렉터리의 .poc.session과 웹 애플리케이션 경로의 poc.session이 생성된 것을 볼 수 있었다. 전자는 취약한 executePartialPut()이 요청 경로 /poc.session의 ‘/’을 ‘.’으로 치환하여 만든 임시 파일이다. 반면 후자는 resources.write()로 생성된 최종 리소스이다. FileStore의 기본 상대 디렉터리도 마찬가지로 해당 애플리케이션의 work 디렉터리를 기준으로 하므로, 이 .poc.session 파일이 이후 세션 복원 대상이 될 수 있다.

조건 5. JSESSIONID 조작을 통한 세션 로드 및 readObject() 실행 검증

Tomcat의 내부 동작에 기반하면, JSESSIONID가 요청됐을 때 PersistentManagerBase.findSession()은 먼저 메모리에서 세션을 찾고, 세션이 없으면 swapIn()과 loadSessionFromStore()를 거쳐 Store.load()를 호출한다. 실습 환경에서는 Store의 구현인 FileStore.load()가 .poc.session 파일을 읽는다. 로드된 세션 속성은 StandardSession.readObjectData()와 doReadObject()를 거쳐 stream.readObject()로 역직렬화된다. 본 실습에서는 exploit을 직접 진행하기보다, 동작 원리 파악에 초점을 맞추어 이 마지막 단계에서 readObject()가 실제 호출되는지 확인하기 위해 SessionProbe를 사용하였다.

그림 6. [역직렬화 동작 확인을 위한 SessionProbe.readObject() 설계]

SessionProbe.readObject()는 세션 역직렬화 과정에서 호출되면 컨테이너 내부에 /tmp/cve-2025-24813-poc 파일을 생성하도록 설계하였다. 다만, 실제 공격과 더 가까운 방식은 역직렬화 공격에 악용 가능한 라이브러리를 활용하기 위해 gadget chain을 사용해주는 것이다. 단순히 세션 파일 역직렬화만 일어났다고 해서 원격 코드 실행이 가능해지는 것은 아니다. 즉, 현재 실습에서 진행한 검증은 공격자 제어 세션 데이터가 서버에서 역직렬화되는 핵심 지점을 확인하는 데 목적이 있다.

그림 7. [Cookie의 JSESSIONID 값을 .poc로 지정]

그림 8. [session = .poc가 확인된 모습]

검증용 SessionProbe가 포함된 세션 파일을 배치한 뒤, Cookie의 JSESSIONID 값을 .poc로 지정하여 세션 로드를 유도하였다. 응답에서 session = .poc가 확인되었으며, 이를 통해 Tomcat이 요청에 포함된 세션 ID를 인식하고 FileStore의 세션 복원 흐름에 진입했다는 것을 볼 수 있었다. 다음으로는 컨테이너 내부의 검증용 파일 생성 여부를 확인해주었다.

그림 9. [payload 동작 확인을 나타내는 /tmp/cve-2025-24813-poc 생성 결과]

위 결과를 통해 확인 파일이 생성되었음을 확인했다. 따라서 partial PUT으로 배치된 .poc.session 파일이 FileStore.load()를 통해 로드되고, StandardSession.doReadObject()의 세션 속성 역직렬화 과정에서 SessionProbe.readObject()가 실행됐다는 흐름이 나타난다.

4. 3. 패치 전후 코드 비교

취약 버전에 해당하는 Tomcat 9.0.98의 executePartialPut()은 사용자 요청 경로의 ‘/’를 ‘.’으로 치환한 값을 임시 파일명으로 사용하였다.

그림 10. [취약 버전 Tomcat 9.0.98의 executePartialPut()의 요청 경로 기반 임시 파일 생성 코드]

한편 패치 버전인 Tomcat 9.0.99에서는 File.createTempFile()을 사용해 요청 경로와 무관한 임시 파일을 만들고, doPut()의 finally 블록에서 사용이 끝난 임시 파일을 삭제하도록 변경되었다.

그림 11. [패치 버전 9.0.99의 요청 경로와 분리된 임시 파일 생성 코드]

결과적으로, 처리가 완료되면 임시 파일이 삭제되는 로직을 통해 공격자가 원하는 이름의 .session 파일을 work 디렉터리에 남겨 FileStore가 읽게 만드는 기존의 공격 흐름이 차단된다.


5. 대응 방안

가장 확실하고 빠른 대응 방법은 Apache Tomcat을 패치 버전으로 업데이트하는 것이다. Tomcat 9.0.99, 10.1.35, 11.0.3 이상을 사용하면 된다. 또한, Default Servlet의 readonly 값이 ‘true’인지 재확인하는 것과 불필요한 PUT 요청을 허용하지 않는 것, FileStore 기반 세션 복원 기능 비활성화를 통해 역직렬화 취약점을 활용한 공격을 예방하는 것도 대응 방안이 될 수 있다.


6. 공급망 보안 관점에서의 의미

요즘, 직접적인 취약점 공격이 어려워짐에 따라 공급망을 우회 경로로 활용한 공격이 증가하는 만큼, 해당 취약점을 공급망 보안 관점에서 바라보는 것도 중요하다. 해당 취약점 자체는 공급망 공격으로 보긴 어려우나, 발생 가능한 공급망 리스크가 무엇인지 해석해 볼 수 있다.

Apache Tomcat은 Java 기반 웹 애플리케이션에서 널리 활용되는 오픈소스 컴포넌트이다. 따라서 기업 내부 시스템, 클라우드 서비스, 개발 프레임워크 등에 폭넓게 포함될 수 있다. 이는 Tomcat과 같은 오픈소스 컴포넌트에서 취약점이 발생하면 단일 서버를 넘어 해당 컴포넌트를 포함하는 제품 전반에 연쇄적인 피해가 발생할 수 있음을 의미한다. 즉, 관련 서비스를 운영하는 조직은 Tomcat을 직접 설치한 서버뿐만 아니라 Tomcat을 내장한 제품과 플랫폼까지 정확하게 식별하고 패치 여부를 꼼꼼하게 확인해야 한다.


7. 결론

CVE-2025-24813은 Default Servlet의 쓰기 기능 활성화, partial PUT 처리 방식에서 기인하는 Path Equivalence 취약점이다. 조건들에 따라 정보 노출 및 파일 변조, 원격 코드 실행으로 이어질 수 있으며 특히 원격 코드 실행의 경우 FileStore 기반 세션 저장과 Java 역직렬화 가능한 classpath가 결합될 때 발생한다. 즉, 해당 취약점은 특정한 기능의 문제점이라기보다 여러 구성요소들의 결합으로 안전성이 저하되는 사례에 해당한다. 따라서 단순한 Tomcat 안전성 문제를 넘어 오픈소스 컴포넌트 관리와 공급망 보안의 중요성까지 확인할 수 있는 사례라고 볼 수 있다.
