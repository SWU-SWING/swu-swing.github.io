[SEED 4월호] CVE-2025-29927: Next.js 미들웨어 우회 취약점

author: bage2room Posted on 2026-04-18 In S.E.E.D. series

1. CVE-2025-29927 취약점

해당 취약점은 오픈소스 자바스크립트 프레임워크인 Next.js에서 발생했다. Next.js의 미들웨어(Middleware)에서 권한 확인이 이루어지는 경우 Next.js 애플리케이션 내에서 권한 확인을 우회할 수 있는 취약점이 발견되었다.

Next.js는 재귀 요청이 무한 루프를 유발하는 것을 방지하기 위해 내부 헤더 “x-middleware-subrequest”를 사용한다. 그러나 이 취약점에서는 내부 요청 판별에 사용되는 “x-middleware-subrequest” 헤더 값을 외부 사용자 요청을 통해서도 임의로 포함될 수 있었고, Next.js 서버가 이를 내부 요청으로 오인하면서 Middleware 실행을 건너뛸 수 있음이 확인되었다. 그 결과, 요청이 라우트에 도달하기 전에 수행되어야 하는 중요한 검사들, 즉 인증 쿠키 검증과 같은 절차를 우회할 수 있게 된다.

1) Next.js Middleware 란?

그림 1. [클라이언트와 서버 사이에서 동작하는 Middleware 구조]

Middleware는 경로 재작성, 서버 측 리디렉션, 응답에 헤더(CSP 등)와 같은 요소를 추가, 인증 및 권한 부여 등을 위해 사용될 수 있다. 가장 중요한 기능인 인증 및 권한 부여에서, 미들웨어는 특정 페이지 또는 API 경로에 대한 액세스 권한을 부여하기 전에 사용자 신원을 확인하고 세션 쿠키를 확인하는 중간 계층의 역할을 한다.

그림 2. [/admin 엔드 포인트 접근 차단]

예를 들어서 사용자가 /dashboard/admin에 접근하려고 하면, 해당 요청은 먼저 미들웨어를 거치게 된다. 미들웨어는 사용자의 세션 쿠키가 유효한지 확인하고 필요한 권한을 부여한다. 권한이 있는 경우 미들웨어는 요청을 전달하고, 그렇지 않은 경우 사용자를 로그인 페이지로 리디렉션한다.

2) 영향을 받는 버전(Target)

  • Next.js 15.x < 15.2.3
  • Next.js 14.x < 14.2.25
  • Next.js 13.x < 13.5.9
  • Next.js 12.x < 12.3.5
  • Next.js 11.x : 11.1.4 이상

3) PoC

Next.js 버전대에 따라 헤더 값에 넣을 미들웨어 이름이 달라진다.

취약 버전 PoC의 헤더 값 예시
v12.2 미만 x-middleware-subrequest: pages/_middleware
v12.2 ~ v14.2 미만 x-middleware-subrequest: middleware
v14.2 이후 x-middleware-subrequest:
middleware:middleware:middleware:middleware:middleware



2. Next.js 버전별 Middleware 특징

1) v12.2 미만 버전

그림 3. [v12.0.1 runMiddleware 함수 내부 x-middleware-subrequest 검증 과정]

Next.js 애플리케이션에서 미들웨어를 사용할 때, runMiddleware 함수가 호출된다. 이 함수는 헤더 값을 가져와 미들웨어를 적용할지 여부를 판단하기 위해 x-middleware-subrequest 요청 헤더를 사용한다. 헤더 값은 colon(:)을 구분자로 사용하여 리스트로 분할된 후, 이 리스트에 middlewareInfo.name 값이 포함되어 있는지 확인한다.

즉 x-middleware-subrequest 요청에 올바른 값을 가진 헤더를 추가하면 미들웨어의 목적과 관계없이 완전히 무시되고, 요청은 미들웨어의 영향 없이 NextResponse.next() 함수를 통해 목적지로 이동할 수 있다.
그렇다면 이를 위한 middlewareInfo.name 의 조건이 무엇일까?

(1) middlewareInfo.name 조건

v12.2 이전에는 파일 이름이 반드시 “_middleware.ts” 이어야 했다.
그리고 pages 라우터만 존재했기 때문에, 미들웨어는 pages 폴더에만 존재해야 했다. (버전 13 이후에 app 라우터가 추가됐다.)
이러한 정보들을 통해 미들웨어의 위치를 추정할 수 있으며, 이에 따라 x-middleware-subrequest 헤더 값을 유추할 수 있다. 헤더 값은 디렉터리 이름과 파일 이름으로 구성된다.

(2) middleware 위치

v12.2 이전 버전에는 pages 폴더 아래 여러 위치에 _middleware 파일을 둘 수 있었고 요청 경로가 깊어질수록 여러 미들웨어가 순서대로 실행됐다.

그림 4. [파일 구조별 middleware 위치 예시]

여기서 주목해야 할 것은 _middleware.ts 파일의 위치다. 만약 사용자가 /about/teams 에 접속하면 Next.js는 pages/about/_middleware.ts를 실행하고, pages/about/teams/_middleware.ts를 실행한 후 최종 페이지에 응답한다. 즉 상위 폴더 미들웨어가 먼저 실행되고 하위 폴더가 후에 실행되는 구조다.

따라서 공격자는 우회를 시도할 때 가능한 경로가 여러 개일 수 있다. 미들웨어로 보호되는 /dashboard/panel/admin의 접근 권한을 얻기 위한 세 가지의 middlewareInfo.name 후보가 있다.

Next.js는 해당 미들웨어가 내부 subrequest에서 실행된 적이 있으면 다시 실행하지 않는다. 따라서 요청 헤더에 x-middleware-subrequest: pages/_middleware 와 같은 값이 들어온다면 pages/_middleware를 이미 실행된 내부 요청으로 인식하고 미들웨어가 실행되지 않고 보호된 페이지로 넘어갈 수 있다. 그러므로 공격이 성공하기 위해선 middleware의 위치를 알고 x-middleware-subrequest 헤더에 올바른 경로 이름을 넣어야 한다.

2) v12.2 ~ v14.2 버전

(1) middlewareInfo.name 조건

v12.2부터는 기존 pages 하위의 _middleware 파일 구조가 사라지고, 미들웨어 파일명이 기존 “_middleware.ts”에서 언더바(_)가 빠진 “middleware.ts”로 변경되었다. 또한 미들웨어는 pages 폴더 내부가 아니라 프로젝트 루트에 위치하게 되면서, 미들웨어 이름 후보는 middleware 하나로 단순화되었다.

또는 /src 폴더를 쓰는 경우가 있다. Next.js는 디렉터리를 생성하는 기능을 제공하여, 프로젝트 루트에 Next.js 전용 앱 또는 페이지 디렉터리를 두거나 애플리케이션 코드를 src 디렉터리 아래에 배치하는 일반적인 패턴을 지원한다. 이 경우 페이로드는 아래와 같다.

즉, v12.2 이후 버전에서는 경로의 깊이와 관계없이 후보가 middleware 또는 src/middleware 두 가지로 단순화된다. 따라서 v12.2 미만 버전과 달리 공격자는 중첩된 pages 경로에 따른 여러 _middleware 위치를 추측할 필요가 없어졌으며, middleware 또는 src/middleware와 같은 제한된 이름 후보만 고려하면 되므로 우회 조건을 파악하기가 더 단순해졌다.

3) v14.2 이후 버전

그림 5. [v.14.2 x-middleware-subrequest 검증 과정]

v14.2부터는 미들웨어의 x-middleware-subrequest 헤더의 값을 colon(:)을 기준으로 나눠서 배열로 저장한다. 저장된 배열에 params.name 변수의 값이 몇 개인지 확인하고, 이 값이 일정 횟수 이상 반복되면 미들웨어를 건너뛰고 요청을 보낸 경로의 응답을 받도록 코드가 변경되었다. 여기서 params.name 은 middleware.name 과 동일한 값이다.

이때 동일한 미들웨어 이름이 일정 횟수 이상 반복된 것으로 판단되면, Next.js는 중복 실행을 방지하기 위해 해당 미들웨어 실행을 건너뛰고 요청 경로의 응답을 반환한다. 그러나 외부 사용자가 해당 헤더 값을 임의로 조작할 수 있었기 때문에, 공격자는 동일한 미들웨어 이름을 반복 삽입하여 서버가 “이미 여러 차례 실행된 내부 서브 요청”으로 판단하게 만들고, 그 결과 미들웨어 실행 횟수 제한 로직을 악용하여 접근 제어를 우회할 수 있다.

따라서, v14.2 이후에는 최대 반복 횟수(MAX_RECURSION_DEPTH) 값이 5로 설정되어 있었으므로, colon(:)을 기준으로 middleware 경로가 5번 이상 반복되면 미들웨어 검증을 우회할 수 있다. “middleware”를 5번 이상 x-middleware-subrequest 헤더에 입력한다.

3. 패치 내역 분석(Patch Diffing)

그림 8. [패치 후 버전의 packages/next/src/server/lib/router-server.ts]

패치 후에는 내부 요청 여부를 외부 사용자가 조작 가능한 헤더 값에만 의존하지 않도록 서버가 crypto.getRandomValues 함수를 사용하여 8바이트의 랜덤 값을 생성하고 ‘@next/middleware-subrequest-id’ 전역 변수에 저장한다. 이 값은 서버가 내부적으로 생성한 일종의 인증 토큰처럼 사용되며, 이후 서브 요청을 처리할 때 요청에 포함된 값과 서버에 저장된 값을 비교하여 실제 내부 요청인지 검증한다.

그림 9. [패치 후 버전의 packages/next/src/server/lib/server-ipc/utils.ts]

x-middleware-subrequest 헤더와 x-middleware-subrequest-id 헤더 값이 존재하는지 확인하고, x-middleware-subrequest-id 헤더 값이 앞서 전역 변수에 저장된 ‘@next/middleware-subrequest-id’와 일치하는지 검사한다. 값이 일치하지 않으면, x-middleware-subrequest 헤더를 삭제하여 이를 활용할 수 없도록 막는다.

사용자는 내부적으로 저장되는 8바이트 난수 값을 예측할 수 없으므로, 서버 측에서는 x-middleware-subrequest 헤더를 안전하게 활용하여 middleware 내부 실행 여부를 판별할 수 있다.
